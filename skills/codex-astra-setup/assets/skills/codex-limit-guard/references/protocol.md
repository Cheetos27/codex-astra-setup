# Checkpoint и возобновление

## Файлы состояния

Выбери приватный доступный для записи каталог артефактов текущей задачи, внутри него `limit-guard/<thread-id>/`. При отсутствии такого каталога допустима локальная игнорируемая папка проекта после проверки, что она не попадёт в Git. Не размещай личное состояние внутри распространяемого навыка. Не используй один checkpoint для всех задач. Подтверди thread id средствами среды; не угадывай его.

Храни `state.json` и `checkpoint.md`. Сначала обновляй checkpoint через временный файл в той же папке и атомарную замену, затем состояние. Только текущая задача пишет в свои файлы. Если запись недоступна, помести компактное состояние в сообщение этой задачи и честно отметь отсутствие файла.

Минимальное состояние:

```json
{
  "version": 1,
  "thread_id": "actual-thread-id",
  "work_id": "unique-current-assignment-id",
  "pause_generation": null,
  "status": "running",
  "checkpoint": "absolute-path-to-checkpoint.md",
  "limit_id": "codex",
  "paused_used_percent": null,
  "paused_resets_at": null,
  "automation_id": null,
  "updated_at": "ISO-8601 UTC"
}
```

Состояния: `running`, `preparing`, `paused_limit`, `paused_user`, `waiting_user`, `cancelled`, `completed`. `preparing` означает, что checkpoint уже создан при 5%, но работа пока идёт. `paused_user` означает ручную паузу, которую восстановление квоты не отменяет. Новый `pause_generation` создаётся один раз на остановку, например UUID; последующие сохранения checkpoint не меняют его. Повторное пробуждение не должно повторно выполнять один и тот же внешний эффект. Среда должна последовательно выполнять ходы одной задачи; навык не устанавливает межпроцессный mutex и не гарантирует exactly-once внешних операций при сбое между действием и сохранением. Перед повтором всегда проверь внешний результат.

Checkpoint содержит:

- поручение, критерий завершения и принятые ограничения;
- что уже сделано и чем проверено;
- абсолютные пути, ветку/commit и незакоммиченные изменения, если есть Git;
- фоновые операции и их состояние; для внешнего действия — известный результат/идентификатор, чтобы проверить, а не повторить;
- точный следующий шаг и оставшиеся проверки;
- ожидаемые ответы пользователя и какие действия уже разрешены;
- причину остановки и время обновления.

«Зафиксировать» здесь означает сохранить файлы и сведения для продолжения. Это не разрешение автоматически коммитить, пушить, закрывать приложения или завершать чужие процессы. Не сохраняй секреты и полные транскрипты.

Минимальная безопасная выборка лимитов для evaluator:

```json
{
  "ordinaryUsageAllowed": true,
  "rateLimitsByLimitId": {
    "codex": {
      "primary": {"usedPercent": 96, "windowDurationMins": 300, "resetsAt": 1900000000},
      "secondary": {"usedPercent": 70, "windowDurationMins": 10080, "resetsAt": 1900500000}
    }
  }
}
```

Передавай дату измерения вместе с рабочим состоянием. Evaluator не получает данные сам: вызывай его только со свежим ответом инструмента. Время `resetsAt` — Unix seconds; не умножай или дели его по предположению.

## Heartbeat

Используй только штатный `automation_update`, `kind: heartbeat`, `destination: thread`, с назначением в эту же задачу. Текущий инструмент требует `destination: thread` или явный подтверждённый `targetThreadId`; не полагайся на неявное назначение. Не создавай вместо него самостоятельный cron-проект, системный планировщик или новую задачу. Не записывай automation.toml вручную.

Перед созданием проверь существующие автоматизации по имени/назначению и id из state. При обновлении сохраняй остальные поля. Имя должно различать задачи, например «Лимиты — <краткое название или id задачи>». Сохрани id ответа в state.

Первое пробуждение должно быть не раньше `resetsAt + 120 секунд` для всех известных блокирующих окон. Вычисли дату из актуального результата и используй подтверждённый формат расписания установленного клиента. До сброса модель не должна получать периодические запросы. Не заменяй будущий первый запуск интервалом 15/30/60 минут от текущего момента. Если время сброса неизвестно или назначение будущего первого запуска нельзя подтвердить, оставь автоматизацию PAUSED, сохрани checkpoint и сообщи, что требуется ручное продолжение после восстановления. Сам статус ACTIVE не доказывает правильное время пробуждения.

При подтверждённом более длительном ограничении, например исчерпанной неделе, учитывай и его `resetsAt`, чтобы не пытаться возобновлять работу после каждого пятичасового сброса. Не предполагай, что недельный сброс уже наступил.

Если `resetsAt` уже в прошлом, а свежая квота не восстановилась, не назначай прошедшее время или немедленный повтор. Приостанови принадлежащую этой остановке автоматизацию. Назначить новый будущий запуск можно только по подтверждённым свежим данным; иначе сообщи о блокере. Поле `retry_after` evaluator — наблюдённая дата, а не готовое расписание.

Промпт автоматизации должен быть самостоятельным. Подставь реальные пути, id задачи и конкретный согласованный результат:

> Применяй $codex-limit-guard к остановке <pause_generation> поручения <work_id> в задаче <thread_id>. Прочитай состояние <путь state.json>, checkpoint <путь checkpoint.md> и новые сообщения пользователя. При несовпадении любого из трёх идентификаторов заверши ход без изменений, включая изменения автоматизации. При совпадении разрешено продолжать только из paused_limit; running и preparing не разрешают возобновление. При отмене, ручной паузе, завершении или ожидании пользователя не работай; отключи автоматизацию только если её текущее назначение всё ещё принадлежит этой остановке. Получи свежие лимиты. Если они ещё не восстановились или недоступны, сохрани паузу и перенеси проверку; не выполняй основную работу. Если восстановились, проверь callback через evaluator, запиши running, приостанови эту автоматизацию и после подтверждения проверь фактическое состояние файлов и внешних операций. Продолжи со следующего незавершённого шага поручения: <конкретная цель>. Не повторяй уже выполненные внешние действия. Не присылай сообщения при неизменном состоянии; сообщай только о возобновлении, завершении, существенном сбое или необходимом решении пользователя.

Проверяй результат создания/обновления, включая статус и следующее время. Если инструмент недоступен, не говори «сам продолжу». Дай путь checkpoint и короткую команду ручного продолжения.

## Проверка поведения

Наблюдение веди в `observation.json` при обычной работе агента, без отдельного периодического модельного heartbeat. 19 сентября 2026 года наблюдатель с интервалом 30 минут оставался ACTIVE, и его сообщения продолжали поступать во время сообщённого пользователем ограничения; состояние не содержало выполненных плановых проверок. Такой цикл не может сам надёжно отключиться, если для выполнения проверки сначала нужна недоступная модель. Автоматизация наблюдения отключена. Сохраняй результаты компактно, не отлаживай и не переписывай навык на последнем проценте. Запрос наблюдать текущую задачу не разрешает обходить остальные задачи.

Реальная остановка записывает в observation идентификаторы поручения/остановки и измеренный остаток как `real_pause_seen`. После срабатывания рабочего heartbeat и первого успешно выполненного шага по тому же поручению/поколению запиши `real_resume_seen` с датой и подтверждением шага, отключи наблюдение и один раз сообщи о проверенном цикле. Тестовые входные данные, создание расписания или одна запись `running` не являются такой проверкой.

Без расходования настоящей квоты проверь: 6% → работа; ровно 5% → подготовка; ровно 1% и 0% → остановка; скачок 7% → 0% → немедленное сохранение; null → неизвестно; истёкшее время при прежнем расходе → продолжения нет; восстановленный лимит при отменённой задаче → продолжения нет; восстановленная пятичасовая квота при исчерпанной неделе → ожидание. Регистрация heartbeat не равна проверке реального сброса.
